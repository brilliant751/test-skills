# 作业 1（中文翻译）

## 1. 作业要求

本作业要求学生使用 AI 方法（例如 LLM）设计并实现（或增强）一种测试技术。可选择方向包括：

- 静态测试
- 黑盒动态测试
- 白盒动态测试

说明：

- 静态测试可参考静态代码分析工具方法。
- 黑盒测试技术包括：等价类划分（EP）、边界值分析（BVA）、输入组合测试、状态迁移测试模型生成、决策表测试。
- 白盒测试可衡量：语句覆盖、分支覆盖、条件覆盖、路径覆盖、d-u 覆盖等。

当前作业要求将方案实现为一个工具，该工具可接收两类输入之一：

1. 系统需求文档
2. 被测代码库

工具需要分析上述输入（需求或代码库/部分模块），并生成测试用例。

## 2. 提交产物（Submission Artifact）

1. 输入：需求文档/项目代码库
2. 工具产物：所用 prompts、所用模型、模型生成代码
3. 生成输出：  
   - 静态分析：报告告警（reported alarms）  
   - 黑盒/白盒分析：测试用例
4. 实验分析：准确率、覆盖率、可泛化性等
5. 项目报告：
   - 与传统非 AI 测试技术的对比、优缺点
   - 分析报告：实践中如何遇到 AI 局限、如何改进工具
   - 总结

## 3. 评分标准（Assessment Criteria）

- 概念理解：10%
- 设计与实现连贯性：20%
- 覆盖与效果/实用性：40%
- 深度分析（泛化性展示、推理等）：20%
- 展示表达：10%

## 4. 展示（Presentation）

- 每组 15 分钟英文汇报，需覆盖上述所有内容。
- 汇报后进行问答。
- 评审会基于提交文档、展示内容，以及学生应掌握的软件测试基础进行提问。
- 组员贡献默认均等。如需调整，必须单独申请并由全体成员签字同意。

每组需在展示日前 1 天通过邮件提交给助教：

2. 最终展示 PPT：首页需包含团队 ID、所有成员姓名和学号。

格式要求：

## 示例提交 Ex1

**标题：** 基于 LLM 的多商品智能售货机动态黑盒测试

### 1) 输入

**系统概述：**  
被测系统为部署在公共区域（如地铁站）的智能售货机。测试者不可见内部软件、硬件控制逻辑和数据库。测试仅基于外部可观察行为，并依据给定需求执行。

**功能需求：**

- R1. 商品选择  
  售货机提供三类商品：  
  - 饮料（价格区间：$1.50-$3.00）  
  - 零食（价格区间：$2.00-$4.50）  
  - 热食（价格区间：$5.00-$10.00）
- R2. 支付方式  
  支持多种支付：  
  - 硬币：$0.10、$0.25、$0.50、$1.00  
  - 纸币：$5.00、$10.00
- R3. 支付约束  
  投入总金额必须大于等于商品价格。找零上限为 $5.00；若需要找零超过 $5.00，则交易被拒绝。
- R4. 库存约束  
  商品可能在支付过程中售罄。

### 2) 工具产物

- 使用模型：GPT-4o
- 示例 Prompt：  

```text
你是一个软件测试助手。给定以下系统概述和需求，请识别：
1) 输入变量
2) 等价类划分（有效/无效）
3) 边界值
4) 具体测试用例
需求：{requirement_text}
```

### 3) 生成输出

- 等价类划分示例（如：投入金额 < 商品价格 / > 商品价格）
- 边界值分析示例（如：商品价格 1.4、1.5、1.6；支付总额 0、1.4、15.1）
- 测试用例示例：  
  - TC1：零食 $3.00，支付 $8.50，预期拒绝（找零 > $5）  
  - TC2：零食 $3.00，支付 $3.50，预期成功并找零 $0.50

### 4) 实验分析

- 4.1 EP/BVA 与测试用例覆盖情况
- 4.2 缺失项分析
- 4.3 通过优化 Prompt 提升覆盖率、准确率和泛化能力

### 5) 项目报告

- 5.1 与传统非 AI 技术的对比与优缺点
- 5.2 AI 局限与改进方式
- 5.3 总结

## 示例提交 Ex2

**标题：** 基于 LLM 的静态分析

### 1) 输入

**系统概述：**  
Axios 是一个基于 Promise 的网络请求库，可运行于 Node.js 与浏览器。该库在原 Axios v1.3.4 基础上适配 OpenHarmony，同时保留现有使用模式和功能：

- HTTP 请求
- Promise API
- 请求/响应拦截器
- 请求与响应数据转换
- JSON 数据自动转换

源码地址：`https://ohpm.openharmony.cn/#/cn/detail/@ohos%2Faxios`

### 2) 工具产物

**示例 Prompt：**

```text
你是一个静态代码分析器。请分析以下 {language} 代码并检测潜在问题。
请识别：
1. 语法错误
2. 安全漏洞
3. 过时或不兼容 API 的使用
4. 潜在运行时错误
5. 代码质量问题

请按结构化 JSON 输出：
{
  "issues": [
    {
      "line": <line_number>,
      "type": "<issue_type>",
      "description": "<detailed description>",
      "severity": "<low/medium/high>"
    }
  ]
}

代码：{source_code}
```

### 3) 生成输出

示例问题（Issue 1）：

- 行号：4
- 类型：资源管理
- 描述：使用 `open` 打开文件但未使用上下文管理器；异常时文件可能未关闭
- 严重级别：medium
- 建议：使用 `with open(filename, 'r') as f:` 自动关闭文件
- 类别：代码质量
- 参考：`https://docs.python.org/3/tutorial/inputoutput.html#reading-and-writing-files`

（另含测试用例/概念验证）

### 4) 实验分析

- 4.1 误报分析
- 4.2 通过优化 Prompt 提升准确率
- 4.3 在更多项目上验证泛化能力
- 4.4 由开发者进行缺陷报告与验证

### 5) 项目报告

- 5.4 与传统非 AI 技术的对比与优缺点
- 5.5 AI 局限与改进方式
- 5.6 总结

### 1) 输入

**系统概述：**

源码地址：`https://ohpm.openharmony.cn/#/cn/detail/@ohos%2Faxios`

### 2) 工具产物

**Prompt：**

```text
你是资深软件测试工程师和白盒测试助手。
你的任务是分析以下 {language} 函数/模块，并生成能够达到“完整语句覆盖”的测试用例集合。

请执行：
1. 识别代码中所有可执行语句
2. 为每条语句生成至少可执行一次的测试输入
3. 以适用于自动化测试的结构化 JSON 输出测试用例

JSON 格式：
{
  "function": "<function_name>",
  "test_cases": [
    {
      "input": { "<parameter_name>": <value>, ... },
      "expected_output": "<expected output or behavior>",
      "covered_statements": [<line_numbers>],
      "notes": "<optional explanation>"
    }
  ]
}

待分析代码：{code_snippet}

说明：
- 如有必要，包含边界用例以覆盖条件分支
- 若某语句因逻辑错误不可达，请标记为 "unreachable"
- 解释每个测试用例如何实现语句覆盖
```

### 3) 生成输出

- 被测函数
- 测试用例  
  - TestCase1：删除指定文件  
  - TestCase2：异常处理

### 4) 实验分析

- 4.1 误报分析
- 4.2 通过优化 Prompt 提升准确率
- 4.3 在更多项目上验证泛化能力
- 4.4 由开发者进行缺陷报告与验证
